The state file is the part of Terraform most people ignore until it bites them — it is the single source of truth Terraform uses to map your configuration onto real-world resource IDs, and mishandling it causes some of the worst outages in infrastructure-as-code. The practical skills are state mechanics, the operations used to fix state when it drifts from reality, and module structures that keep a growing codebase composable instead of becoming an unmaintainable monolith.

## What state is and why it exists

Terraform state is a JSON record mapping each resource block in your configuration to the real-world object it created — a specific cloud resource ID, its last-known attribute values, and dependency metadata. Terraform needs this because HCL alone doesn't identify *which* real object a `resource "aws_instance" "app"` block refers to; without state, every `plan` would have to guess or ask, or worse, assume nothing exists yet and try to recreate everything.

> [!KEY]
> State is not a cache you can casually regenerate. It is the only link between your configuration and the resources that actually exist — lose it, and Terraform's next plan will not know those resources are yours.

## Remote backends and state locking

Storing state as a local file works for a solo experiment and fails the moment a second person or a CI job runs Terraform concurrently — two applies racing against the same local file corrupt it or silently overwrite each other's changes. A **remote backend** (Azure Storage, S3 + DynamoDB, Terraform Cloud) centralises the state file and adds **locking**: while one run holds the lock, any concurrent `plan` or `apply` blocks or fails fast instead of racing.

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstateacctprod"
    container_name       = "tfstate"
    key                  = "checkout/prod.tfstate"
  }
}
```

> [!DANGER]
> Never commit `terraform.tfstate` to version control. It routinely contains resource attributes in plain text — database passwords, connection strings, private keys generated by a resource — and it has no locking, so two people editing the repo concurrently can corrupt it. Always use a remote backend with locking.

## State file structure and safe inspection

The state file is JSON: a `resources` array, each with a `type`, `name`, and one or more `instances` holding the actual `attributes` (the full resource state as last read from the provider) and dependency metadata. You can inspect it safely without ever hand-editing the file:

```bash
terraform state list                       # every resource Terraform is tracking
terraform state show aws_instance.app      # full attributes of one resource
terraform show -json | jq '.values'        # machine-readable full state
```

## Import, move, and remove

| Operation | Command | When to use |
|---|---|---|
| Import | `terraform import aws_instance.app i-0abc123` | A resource exists in the cloud but isn't in state yet (created manually or by another tool) |
| Move (rename) | `terraform state mv aws_instance.old aws_instance.new` | Renaming a resource in code without destroying and recreating it |
| Move (module refactor) | `terraform state mv module.old.aws_instance.app module.new.aws_instance.app` | Restructuring code into/out of a module without touching real infrastructure |
| Remove | `terraform state rm aws_instance.legacy` | Stop managing a resource in Terraform without destroying it |
| Modern syntax | `moved { from = ... to = ... }` block in HCL | Same as `state mv`, but declarative and committed to code, so it survives for every teammate automatically |

```hcl
# Declarative alternative to `terraform state mv`, checked into the config itself
moved {
  from = aws_instance.old
  to   = aws_instance.new
}
```

> [!TIP]
> Prefer the `moved` block over manual `terraform state mv` where possible — it's committed alongside the refactor, so anyone who pulls the change gets the correct state transition automatically instead of needing a manual out-of-band command.

## Drift detection and reconciliation

Drift is any gap between state and real infrastructure caused by something other than Terraform — a manual console change, another automation tool, or a cloud provider auto-healing an attribute. `terraform plan` (which refreshes against real infrastructure by default) surfaces drift as an unexpected diff. Reconciliation means deciding, per drifted attribute, whether to accept reality (`ignore_changes`, or updating the config to match) or to have Terraform revert it back to the declared value on the next apply.

> [!WARNING]
> Frequent, unexplained drift on the same field is usually a sign that *something else* is also managing that resource — an autoscaler, a manual runbook, another pipeline. The fix is process (stop the other write path or explicitly `ignore_changes` on that field), not repeatedly re-applying and hoping it stops.

## Workspaces vs directory-per-environment

| | Terraform workspaces | Directory per environment |
|---|---|---|
| Isolation | Same config, separate state per workspace | Separate config directories, separate state |
| Risk of cross-environment mistake | Higher — one `terraform workspace select` typo applies to the wrong env | Lower — you can only be in the directory you're in |
| Config drift between envs | None — literally the same files | Must be deliberately kept in sync (modules help) |
| Recommended for | Short-lived, throwaway variants (per-PR preview envs) | Long-lived environments (dev/staging/prod) |

**Recommendation:** use directory-per-environment (each environment as its own root module, calling shared child modules) for dev/staging/prod. The blast radius of a wrong workspace selection against production is too high a price for the convenience of one shared config; a root module per environment makes "which environment am I about to change" a property of *which directory you're in*, not a runtime flag you have to remember to check. Reserve workspaces for genuinely ephemeral, same-shaped variants like per-branch preview environments.

## Module design

A module is a reusable, parameterised package of resources — inputs (`variable`), outputs (`output`), and the resources in between. Good modules are versioned (via a registry or a Git tag/ref) so consumers pin to a known-good version rather than always tracking the module's `main` branch.

```hcl
module "app_service" {
  source  = "app.terraform.io/myorg/app-service/azurerm"
  version = "~> 2.3"

  name_prefix = local.name_prefix
  sku_name    = "P1v3"
  tags        = local.common_tags
}
```

| Concept | Root module | Child module |
|---|---|---|
| What it is | The configuration you `apply` directly | Called via a `module` block, reusable |
| Owns the backend | Yes | No — inherits the caller's backend/state |
| Typical content | Environment wiring, calls to child modules | A cohesive unit — "a web app", "a VPC" |

A root module per environment composes several small child modules rather than containing every resource directly:

```mermaid
flowchart TD
    Root["Root Module<br/>(production environment)"] --> Net["module: network"]
    Root --> App["module: app-service"]
    Root --> DB["module: database"]
    App --> Net
    DB --> Net
```

## Keeping modules small and opinionated

The failure mode to avoid is a single giant module with fifty optional variables trying to cover every possible use case — it becomes unreadable and every consumer sets a different subset of flags. Better: small, opinionated modules that do one thing well, compose several together at the root level, and expose only the inputs that genuinely vary between callers. If two teams need meaningfully different behaviour, that's a signal for two modules, not one module with a toggle for each team's preference.

## Testing infrastructure as code

| Technique | What it catches |
|---|---|
| `terraform validate` | Syntax errors, type mismatches |
| `terraform plan` in CI on every PR | Unexpected diffs before merge, including accidental recreates |
| Policy-as-code (OPA/Conftest, Sentinel) | "This S3 bucket must not be public", org-wide guardrails |
| `terraform test` / Terratest | Actually apply to a throwaway environment, assert real behaviour, then destroy |
| Static analysis (tflint, checkov) | Provider-specific best-practice violations, security misconfigurations |

## Sample module

```hcl
# modules/app-service/variables.tf
variable "name_prefix"  { type = string }
variable "sku_name"     { type = string, default = "P1v2" }
variable "tags"         { type = map(string), default = {} }

# modules/app-service/main.tf
resource "azurerm_resource_group" "this" {
  name     = "${var.name_prefix}-rg"
  location = "westeurope"
  tags     = var.tags
}

resource "azurerm_service_plan" "this" {
  name                = "${var.name_prefix}-plan"
  resource_group_name = azurerm_resource_group.this.name
  location            = azurerm_resource_group.this.location
  os_type             = "Linux"
  sku_name            = var.sku_name
}

# modules/app-service/outputs.tf
output "resource_group_name" {
  value = azurerm_resource_group.this.name
}
```

## Cheat sheet

- State maps your config to real resource IDs — without it, Terraform cannot know what already exists.
- Always use a remote backend with locking; never a local state file for anything shared.
- Never commit state to version control — it routinely contains secrets in plain text.
- Import brings unmanaged resources into state; `state mv` / `moved` blocks rename or restructure without recreating; `state rm` stops managing without destroying.
- Prefer `moved` blocks (committed to code) over manual `state mv` (a one-off command someone has to remember to run).
- Recurring drift on the same field usually means another system is also writing to it — fix the process, not just the state.
- Directory-per-environment for dev/staging/prod; workspaces for short-lived, same-shaped variants.
- Small, opinionated modules that compose beat one giant module with fifty flags.
- Version-pin modules from a registry; test with `plan` in CI, policy-as-code, and `terraform test`/Terratest for real applies.

## Common mistakes

| Mistake | Fix |
|---|---|
| Committing `terraform.tfstate` to Git | Use a remote backend; add `*.tfstate*` to `.gitignore` |
| Local state with multiple people/CI applying | Remote backend with locking (S3+DynamoDB, Azure Storage, Terraform Cloud) |
| Hand-editing the state JSON file | Use `terraform state` subcommands or `moved` blocks instead |
| Using workspaces for dev/staging/prod | Use directory-per-environment; reserve workspaces for ephemeral variants |
| One module with fifty optional flags | Split into small, opinionated modules composed at the root |
| Ignoring recurring drift by re-applying repeatedly | Find and stop the other write path, or explicitly `ignore_changes` |
| Unpinned module `source` (tracking a branch) | Pin a registry version or Git tag/ref |

## Summary

Terraform state is the authoritative map from your HCL to real infrastructure IDs, which is why it must live in a locked remote backend and must never be committed to version control or hand-edited. Import, `state mv`/`moved`, and `state rm` are the safe tools for reconciling state with reality without destroying and recreating live resources, and recurring drift is usually a signal that something else is writing to the same resource. Directory-per-environment gives dev/staging/prod a safer blast radius than workspaces, and modules should stay small, opinionated and versioned rather than growing into one configurable monolith — composed together at the root, tested with `plan` in CI and policy-as-code before anything reaches production.

## Top Interview Questions

### Q1. What is Terraform state, and why can't Terraform work without it?

State is a JSON file that maps every resource block in your configuration to the actual object Terraform created for it — its real cloud resource ID, its last-known attributes, and dependency ordering. Terraform needs this because your HCL alone only describes *desired* resources; it has no inherent way to know that `resource "aws_instance" "app"` corresponds to instance `i-0abc123` specifically, versus some other instance, or none at all. Without state, every plan would have no memory of what was previously created, so it could only guess — either assuming nothing exists (and trying to recreate everything, causing duplicate resources or errors) or requiring you to manually reconcile constantly.

### Q2. Why should Terraform state always live in a remote, locked backend instead of a local file?

A local state file has no concurrency protection — if two people, or a person and a CI job, run `apply` at close to the same time, they can race on writing the same file, corrupting it or silently discarding each other's changes. A remote backend (S3+DynamoDB, Azure Storage, Terraform Cloud) centralises the file so everyone reads and writes the same copy, and adds locking so a second concurrent run blocks or fails cleanly instead of racing. It also solves a practical problem beyond safety: a local file lives on one person's laptop, so nobody else, and no CI pipeline, can run Terraform against that environment at all without it.

### Q3. Why should you never commit the Terraform state file to version control?

Two reasons. First, security: state routinely contains sensitive values in plain text — a generated database password, a connection string, a private key output by a resource — because Terraform needs the real attribute values to compute future diffs, and it doesn't redact them. Committing that to Git means every person with repo access, and every fork or clone ever made, has that secret in history forever, even if you delete it later. Second, correctness: Git has no locking, so two people committing conflicting state edits produces a merge conflict in a JSON blob that is extremely easy to resolve incorrectly, silently corrupting Terraform's view of reality.

### Q4. A database was created manually in the cloud console before your team adopted Terraform. How do you bring it under Terraform management without recreating it?

I'd write a `resource` block in HCL matching the existing database's configuration as closely as possible, then run `terraform import aws_db_instance.primary <the-real-resource-id>` (or the equivalent `import` block in newer Terraform versions), which populates the state file with that resource's real attributes without calling any create API. Critically, import doesn't generate the HCL for you — after importing, I'd run `terraform plan` and iterate on the resource block until the plan shows no changes, confirming my configuration now accurately describes the existing resource rather than planning to "correct" it into something different and potentially destructive.

### Q5. What's the difference between `terraform state rm` and actually destroying a resource?

`terraform state rm` removes a resource from Terraform's state file only — it does not call any delete API against the real infrastructure, so the resource keeps existing and running exactly as before, Terraform just forgets about it and will no longer manage or report drift on it. An actual `destroy` (or a plan showing a `-` delete) calls the provider's real delete API and the resource stops existing. I'd use `state rm` when handing a resource off to be managed elsewhere (another team's Terraform config, or manually) without any interruption to the resource itself, and reserve destroy for when I actually want the object gone.

### Q6. How do `terraform state mv` and a `moved` block accomplish the same thing, and why would you prefer one over the other?

Both tell Terraform "the resource that used to be identified as X is now identified as Y, don't destroy and recreate it" — useful when you rename a resource in code, or move it into or out of a module, without wanting Terraform to interpret that as delete-old/create-new. `state mv` is an imperative, one-off command run against the state directly; a `moved` block is the declarative equivalent, written into the HCL itself and applied automatically on the next `plan`/`apply` by anyone who pulls that code. I'd prefer the `moved` block for anything committed to a shared repo, because it travels with the refactor — a teammate who pulls the renamed resource doesn't need to separately remember to run a state command; someone using `state mv` alone can easily forget, and their next plan will show a spurious destroy/recreate.

### Q7. You notice `terraform plan` keeps showing the same field as changed, reverting back every time you apply. What's going on and how do you handle it?

This is classic drift caused by something else also writing to that field outside Terraform — a common example is an autoscaler adjusting a `desired_count` or replica count that Terraform's config declares as a fixed value; every apply resets it, and the autoscaler changes it back shortly after. Repeatedly applying doesn't fix anything, it just fights the other system. The right fix is to add that specific attribute to `lifecycle { ignore_changes = [...] }` so Terraform stops trying to own a field that's legitimately managed elsewhere, while continuing to manage everything else about that resource normally.

### Q8. Would you use Terraform workspaces or separate directories for managing dev, staging, and production? Justify your answer.

I'd use directory-per-environment for dev/staging/prod rather than workspaces. Workspaces share the same configuration files and only vary the state per workspace, which means the boundary between "I'm about to change staging" and "I'm about to change production" is a runtime selection (`terraform workspace select prod`) that's easy to get wrong under time pressure — a single typo or stale terminal session applies your change to the wrong environment. Directory-per-environment makes that boundary a property of the filesystem: you can only apply to the environment whose directory you're actually in, and each environment can have deliberate, reviewed differences (instance sizes, replica counts) expressed explicitly rather than hidden behind conditionals. I'd reserve workspaces for genuinely short-lived, identically-shaped instances of the same config, like a temporary per-pull-request preview environment.

### Q9. How would you design a Terraform module so it stays maintainable as more teams start using it?

I'd keep it small and opinionated rather than trying to cover every possible variation with an ever-growing list of optional flags — a module that does one clear thing (provision a web app, a VPC, a queue) with a handful of well-named inputs is far easier to reason about than one with fifty toggles where most consumers only ever set five of them. I'd expose only the inputs that genuinely need to vary between callers, version it (a registry version or a Git tag) so consumers pin to a known-good release instead of tracking a moving branch, and if two teams need meaningfully different behaviour, I'd treat that as a signal to split into two modules rather than adding a branching flag to one.

### Q10. How do you test Terraform code before it reaches production?

Layered, cheapest first: `terraform validate` catches syntax and type errors immediately; `terraform plan` running in CI on every pull request surfaces the actual diff a change would make, including catching an unexpected destroy-and-recreate before merge; static analysis tools like tflint or checkov catch provider-specific misconfigurations (a public S3 bucket, a missing encryption setting); policy-as-code (OPA/Conftest, Sentinel) enforces org-wide guardrails as an automated gate rather than a manual review checklist. For anything higher-stakes, I'd use `terraform test` or Terratest to actually apply the module against a throwaway environment, assert real runtime behaviour, and tear it down — that's the only layer that catches problems the static checks can't, at the cost of being slower and needing real cloud credentials in CI.

### Q11. What's the risk of a module with an unpinned `source`, like tracking a Git branch instead of a tag?

If a module source points at a moving branch (`main`) rather than a fixed version, every `terraform init` (or a lock-file-less run) can silently pull in whatever the module's maintainer has since pushed — a changed default, a renamed variable, a different resource entirely — with no signal to the consumer that anything changed until the next plan shows unexpected diffs, or worse, until after an apply. Pinning to a specific registry version or Git tag/ref means upgrading the module is a deliberate, reviewed action (bump the version, read the changelog, test the plan) rather than something that happens implicitly to everyone using that module the next time they run Terraform.

### Q12. How would you recover if the Terraform state file for a production environment was accidentally deleted?

First, I would not run `apply` immediately — with no state, Terraform believes nothing exists and will try to create everything from scratch, which for most resources means duplicate infrastructure or naming collisions and errors, not a clean recovery. Instead I'd check if the remote backend has versioning (S3 versioning, Azure Storage soft-delete) and restore the previous version of the state object directly — this is the primary reason to enable object versioning on the state backend from day one. If no backup exists, the recovery path is systematically running `terraform import` for every resource currently running in the account/subscription to rebuild the state file from real infrastructure, which is slow and error-prone — a strong argument for treating remote backend versioning as a non-negotiable setup step, not an afterthought.
